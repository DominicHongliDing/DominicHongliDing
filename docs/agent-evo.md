# Agent EVO · 评测与改进工作台

从一次有问题的回答，走到一项可以验证的改进。

[查看源码与运行说明](https://github.com/DominicHongliDing/Agent-EVO) · [查看公开案例](https://dominicspace.com/apps/evaluation/index.html?space=history&view=story) · [返回个人主页](../README.md)

## 为什么会做它

在做 UniHR 和 Clinical Agent 时，我发现“页面有结果了”和“用户的事情做好了”之间还有一段距离。文件可能生成了，却漏了字段；医生补充了新信息，下一轮回答却仍沿用旧条件。只看最终回答，很难分清问题在哪，也难判断一次改动是否有效。

EVO 面向需要验收和迭代 Agent 的产品负责人、业务审核者，以及配合接入和修复的开发者。它把一次评测组织成连续的工作：先约定任务完成的标准，再看结果、核对问题、比较版本，最后保留可重复使用的测试场景。

## 用户怎样开始

| 手头有什么 | 从哪里开始 | 接下来能做什么 |
|---|---|---|
| 已有问答或对话记录 | 导入回答 | 按预期审核，定位缺口，把确认的问题留下来 |
| 可以调用的 Agent | 连接自己的应用，再选择测试集 | 取得新回答，用同一组问题比较版本 |
| 只有业务场景，还没有测试题 | 描述服务对象、任务和不能做的事 | 查看 AI 生成的草稿，修改并确认测试要求 |

公开 Clinical 案例用于了解评测方法。自己的 Agent 应使用对应业务场景与验收要求。

## 几个影响产品形态的选择

### 先明确要做的决定

一次评测可能是检查当前质量，也可能是比较版本、验证已知问题。入口先问清目的，再展示所需步骤，减少用户在配置和图表之间找路的负担。

### 每个问题都能回到原始记录

结果页关联用户输入、实际回答、预期要求与执行证据。模型给出的疑似原因仍然需要核对；证据不足时，保留待确认状态。产品人员据此和研发讨论排查方向。

### 改过之后，还要用同一道题验证

确认有价值的失败案例可以整理为回归题。修复后再次执行，对照原来的问题与要求，检查它是否消失，也检查是否影响其他场景。这样，下一轮迭代能接着已有判断往前走。

## AI 在里面做什么

AI 根据产品说明起草测试题，按明确标准辅助评审回答，并整理问题报告。规则检查处理字段、格式和已定义的约束；业务人员审核预期与判决。测试题、实际结果和判断分别保存，避免把模型自己写出的答案直接当成标准答案。

连接器让应用可以留在自己的电脑、内网或云服务里执行，平台收集约定的结果与证据。它服务于已有问答和多轮对话应用；具体接入仍需要开发者配合。

## 从一个实际案例看设计

公开合成对话里，用户把病程“两周”更正为“三天”，再要求总结。第二轮回答没有体现这次更正。对产品而言，需要验收的是“后续回答是否采用最新信息”，因此要保留前后两轮记录、明确预期，并据此安排复测。

这个案例让我把关注点从单条回答的流畅程度，移到连续任务是否完成。它也成为 EVO 展示问题、保留依据和组织回归测试的出发点。

## 当前可以看到什么

在线版本提供 Clinical 公开案例，以及回答导入、测试集、评审与版本对比等入口；真实模型调用需要相应配置。平台仍在迭代，真实用户的首次使用与业务校准需要继续验证。Clinical 案例使用合成测试材料，医疗判断仍需专业医生审核。
